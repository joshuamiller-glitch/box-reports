# DS3_TAPE_DEDUP - scope of the duplicated Sunday-open hour(s) in the monthly trade-tape files (agent TAPE-1, 2026-10-31)

Research only. No live / execution / chart change. Originals never modified. Trade dates read <= 2026-02-06 (disclosure of one slip in section 7). OMP/MKL = 1, 2 workers. Code `l2vast/ds3/code/tape_dedup/`, outputs `l2vast/ds3/out/tape_dedup/` (de-duplicated copies, manifest) and `l2vast/ds3/out/tape_dedup_rescore/` (re-scores).

## PAGE 1

**Verdict.** The defect is real and exactly as ALT-A described, but it is wider than the bar store: the monthly tape files of NQ, ES and RTY carry it, and so do the tick library and everything built on its tick cache. The 1-s path arrays, the 1-min library, the L2 1-s / 1-min / 100-ms tables, the trade library and the lock engine are clean on all 11 days (tested, exact). **No number in DS3_SUNDAY_BRIEF.md changes** (SS-2 / D6 composite, lock-engine risk, ER sizer, zones, persistence): the one store-dependent input, the PE 45-s three-bar confirmation, differs on 115 of 89,464 events and none of them is in a NY session, where the confirmation is used. BARS-CAND tiers move by at most 1 of 68 representatives (LEAD to DEAD, a threshold crossing); the registered "0 PASS, bar types are not a base" conclusion stands.

**1. The defect, precisely.**
* 13 NQ monthly files (2023-04, 07, 10; 2024-06, 09, 12; 2025-02, 03, 06, 11; 2026-02, 03, 08) start with a stray copy of the Sunday-open hour(s): rows [0,b) (b = 3,603 .. 19,881) are followed by ONE timestamp step backwards (the month's first ts re-appears) and then the same prints again in normal order. Head = 2 h in EDT months (22:00Z open), 1 h in EST months (23:00Z). Rows [0,b) equal rows [b,2b) element-wise in all 29 files checked (NQ 11, ES 9, RTY 9 inside the cap; ts, seq, instr, px, sz, side, flags). Prices are unaffected; print count and volume of that hour are exactly doubled (tape = 2.00x the L2 tables in the 2-h cases; 1.4-1.7x over a 3-h window).
* ES (from its first file 2023-08) and RTY have it in the same months from 2023-10: 9 files each inside the cap (11 each incl. 2026-03 and 2026-08, not processed). Inside the 2026-02-06 cap: NQ 11, ES 9, RTY 9 = 29 files. The 11 NQ label days are the ones listed in the task; 20260202 is the only one in the last-10-day window.
* **Pattern: every month whose first session opens on the weekend (the 1st is a Saturday or Sunday) is defective, 13 of 13; no other month is (32 of 32 existing).** Suspected mechanism (not traced to a cause): `l2vast/l2v_reduce.py` line 253 writes the first UTC-day segment of a raw month file twice (`cat([seg, seg])`, "row 0 dropped"); in a weekend-start month that first segment is just the 1-2 h Sunday-open fragment. **Forward warning:** the same defect is already in the weekly ext tape `2026-10__ext_20261024_20261030` (NQ, ES, RTY: 1 back-step each, first ts 2026-10-25 22:00Z; ts-only look), and the 2026-11 monthly file (month starts Sunday 2026-11-01) will have it. The weekly extension procedure must de-duplicate before building (script below).
* Reference check: after de-duplication the tape volume equals the L2 1-min table volume in all 29 files (ratio 1.0000; one RTY file 1.0008), and for the 11 NQ days equals the library day volume exactly (0 contracts of 6.8 M).

**5. Minimal fix and cost.** Block de-duplication, not key de-duplication: `(ts, seq)` is NOT unique (2023-04: 403,040 repeated (ts,seq), 71,446 repeated full keys, only 10,309 true replay rows), so a key-based drop would delete ~61 k genuine prints in that file. Rule (`tape_dedup.py`): b = the single back-step; verify rows[0:b] == rows[b:2b] (or sub-multiset); drop rows[0:b]; assert monotone ts and row count. Run so far: `--write` produced de-duplicated copies of 29 files (NQ 11, ES 9, RTY 9) in `out/tape_dedup/<INST>/YYYY-MM.parquet` (manifest.csv, verify_vs_l2_1min.csv); `--link NQ` builds a drop-in TAPE directory (`out/tape_dedup/NQ_dropin/`: symlinks to clean months, de-duplicated files for defective ones). Cost: de-duplication of 29 files a few minutes; store rebuild of the 11 months 533 s CPU (0.15 h; all 35 months ~0.5 h; `store_rebuild_scratch.py`); BARS-CAND L tables for 22 series ~4 min wall at 2 workers plus 10 min cellstats (`run_barcand_rebuilt.py`, `rescore_bars_cand.py`); rebuild of wave-2 daily tables, CF streams and rankings not measured (day-drop bounds above). Recommendation: do NOT rebuild anything before Sunday; after Sunday (a) patch the reducer / de-duplicate every new weekly ext and monthly file before it enters the library, (b) rebuild the 11 store months from `NQ_dropin` (cost above) when the next store consumer is re-run, (c) re-run BARS-CAND only if the tier table is to be re-issued (1 flip).

### 6.3 Caveats of the re-score
* Day-drop removes legitimate trades on those days (NY sessions of the same label day) and does not remove carry-over of recursive indicators into later bars; the rebuild is the correct reading, the drop is the conservative bound. They agree except at thresholds.
* The rebuild run freezes the realised bars-per-minute (`bpm`) of the old store: `bpm` = n_bars / n_1m_bars sets the grouping factor g = round(...) of the 'G' variants (ALT-B: round(2.4999) = 2), and removing the extra bars moves it by ~0.3-1%; an unfrozen first run changed rows on days outside the 11 (`daily_rebuilt_check.csv`). Whoever rebuilds for real must decide whether to freeze g. After freezing, days outside the 11 differ in <= 231 rows per series of ~500 k (recursive-indicator carry-over).
* G4 (placebo, 200 draws) and G6 (cumulative multiplicity) were not re-run; stored placebo ranks are carried for the 68 reps (the replay changes at most 2 trades of any rep).
* BARS-CAND-2 groups use the stored selection files; GRID, ICT, BAR-ENG, CF-BARS were not re-scored (bounds only).
