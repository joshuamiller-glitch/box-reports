# DST_AUDIT_20261105 - US DST ended 2026-11-01 02:00 ET: audit of standing / Shadow / monitor / feed code (DST-1, CAL)
Read-only audit and TEST. No code was edited; every fix below is proposed text for the owner. Tests and traces: `/mnt/l2/l2vast/ds3_base4/dst_audit/{dst_test.py, dst_test2.py, dst_test3.py, *.json}`. ET = America/New_York. From 2026-11-01 02:00 ET: EDT (UTC-4) -> EST (UTC-5): 09:30 ET = 13:30Z before, **14:30Z** from 2026-11-02; the Sunday 18:00 ET session open = 23:00Z (22:00Z before); 16:55 ET flat = 20:55Z before, **21:55Z** after.

## 0. Verdict
1. **No live-facing (D7-read) file is affected by the DST change.** The code D7 would run (`shadow2_books.py`, `fade_books.py`, `nyam_books.py`, `sizer_lines.py`, `shadow_register.py`, `d6_state.py`) and every Monday runner, `fills_join.py`, `live_monitor.py`, `hm_feed.py` (tape build), the engine harness (`book_harness`, `fpbuild`, `fade_engine`) convert with the tz database (`ZoneInfo('America/New_York')` / `tz_convert`), never with a fixed offset. All synthetic tests straddling 2026-10-30 (EDT) and 2026-11-02 (EST) map correctly (section 3).
2. **What does break or is wrong** (section 2): (a) `autopilot/join_recon2/jb_*.py` hard-code `hours=4` (wrong for every live fill from 11-01; offline JOIN_RECON scripts); (b) `bt_forward_check.load` (the BT Monday runner) buckets by UTC date and UTC-midnight weeks and **drops the first forward hour** (Sun 11-01 18:00-19:00 ET); (c) `hm_feed.py:17` / `pull_nov.py:15` forward floor is 22:00Z = 17:00 EST, not the 23:00Z Sunday open (harmless one empty hour, but inconsistent with the 23:00Z floor in the scorers); (d) `p9_replay.py` / `patch_fast.py` DST tables stop at 2026 (wrong from 2027-03-14); (e) the NT8-faithful research engines use a **fixed UTC-4 clock** (HM VWAP reset "00:00 UTC-4", B8 session windows): in winter that is 23:00 EST, and it is **not known whether the live platform does the same**; the live behaviour was only ever observed in EDT. This is a QUESTION for the platform owner (section 4), not a code bug.
3. **One unrelated bug found while testing:** `parse_d6_output_log.py:76` counts the sub-second part twice (a time of `...:02.123456` becomes `...062246` ms instead of `...062123`): up to +999 ms on every parsed signal/fill time (section 2, item 7).

## 1. How the audit was done
Grep of 69 files (zones3/standing, shadow2, sizer_shadow, nyam, fade_shadow, bt_forward_weekly, shadow/*, hmfwd, fade_engine, fade_books, shadow_register, jb_prep/jb_worker) and of `autopilot/` + `code/` for: `hours=4/5`, `Timedelta(hours=`, `-04:00/-05:00`, `EDT/EST`, `UTC-4/5`, `14400/18000`, `3600*4`, `13:30/14:30`, `% 86400`, `.hour`, `fromtimestamp`, `tz_localize`, `ZoneInfo/pytz`, hard-coded epoch floors; then reading each hit. `hm4` columns: `code/census/night_ins/ap_ext_h2.py:33-35` (`u4 = ts - Timedelta(hours=4)`).

## 4. Questions for the platform owner (potentially live-facing)
1. **HM VWAP reset clock.** The research replica of the live HM book resets its session VWAP at 00:00 on a fixed UTC-4 clock and was validated on live data from April-October 2026 (EDT only), where "fixed UTC-4" and "ET midnight" are the same instant. From 2026-11-02 they differ by an hour (23:00 EST vs 00:00 EST). Does the D6/NT8 HM book reset at (a) 00:00 local exchange time (moves with DST), (b) 00:00 fixed UTC-4 (stays at 23:00 EST), or (c) at the 18:00 ET session start? Test once the first full winter HM week is in StratTrades (11-02..11-06): replay HM with both anchors and compare entry times.
2. The B8/NT8-faithful engines also model entries 18:05-16:40, guards 15:00-16:50 and 09:00-10:00 "on the UTC-4 clock" (th_audit/report_text.py rows 11-12); the live D6 uses ET windows with the 16:55 ET flat, so this only matters for those research replicas.
3. NT8 Output-log timestamps: `parse_d6_output_log` assumes `America/New_York` local times; confirm the platform machine's tz is ET (the first winter log line, 2026-11-02, must read 14:xx Z for a 09:xx ET entry).
