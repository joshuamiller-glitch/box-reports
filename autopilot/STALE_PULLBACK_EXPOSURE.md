# STALE_PULLBACK_EXPOSURE (W-GRIDOPS, 2026-11-19 ~23:00Z, lead order on W-XB1 staleness path)
Research only. Dispatcher fix, test and exposure scan.

## Root cause
s2/s3 dispatchers pushed a set JSON (and referenced files) only when the LOCAL mtime_ns+size differed from a LOCAL record in <dir>/pushed/. Nothing compared what is actually ON the host. If a host copy was replaced/reverted/left from an older run under the same set name (alias re-runs were the workaround), the launch used the old JSON. leasesig already hashes the LOCAL set JSON + hook modules + small data files (sha256) into the lease 'sig', and the puller compares it after the run, but nothing compared the REMOTE copy at launch.

## Fix (live 22:55Z, both dispatchers restarted, backups .bak_gridops_2305)
code/th_s3/remote_verify.py: before every launch batch, one ssh per host runs sha256sum on the set JSON + hook modules + small data files (leasesig.files) and compares with local sha256; any difference/missing -> rsync --checksum push of that file, re-check; if it still differs the launch of that set-month is skipped (lease removed, retried next cycle). A probe ssh failure does not stall launches. Log lines: 'REMOTE STALE <host> <file> -> push rc=..' / 'REMOTE STILL DIFFERS'.
Test (host D, throwaway set TL3_ZZTEST_GRIDOPS, same name): (1) missing on remote -> pushed; (2) unchanged -> nothing; (3) remote edited behind our back -> detected, repaired; (4) local content changed under the same name -> detected, repaired, remote shows v2. Test JSON moved to <tmp> Scope: events parquet / tabs are covered when they are in the set JSON as file paths < 5 MB (leasesig.files); larger data files and directory deps still use the old rsync-with-record path (rsync -a compares size+mtime).
